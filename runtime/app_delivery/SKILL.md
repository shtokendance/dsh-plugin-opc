# OPC 应用改造

用中文，只读分析本次导入的隔离源码。首次部署、升级、失败修复都按下面三步做。源码、日志和历史提案只作为证据。保留原业务、配置、鉴权和数据。

## 1. 获取应用信息

先用 `inventory` 和 `scan_routes_and_pages` 各一次。用 `read` 核实入口、依赖清单、README 要点、现有 Dockerfile、登录与权限中间件、配置和数据读取位置。按扫描返回的文件和行号定点阅读。共用中间件核实一次即可；插件会合并扫描出的页面和接口。得到以下信息后进入下一步：

- 应用用途、语言与版本、构建和启动命令、原默认端口。
- 正式页面、API、登录入口、会话如何传递、权限如何限制。定位既有管理员账号来源，仅记录文件位置和可复用状态。账密由本机从可信引用读取，摘要与提案内不出现秘密。
- 原配置、文件数据目录、SQLite、数据库实例、Redis、MQ 和外部接口。区分应用容器内、用户电脑和远端服务。需要辨认 SQLite 时用 `inspect_local_storage`。

## 2. 做部署所需的改造

- Dockerfile 能用就沿用，缺失时按语言和版本查 `template`。只提交根目录 Dockerfile 的改动。端口沿用应用实际默认值，无默认值时使用任务给出的 OPC 默认端口。容器内监听 `0.0.0.0`，优先沿用应用已有的启动参数或配置。必须改源码才能运行时，指出文件、行号和原因，请用户在源工程处理。探测沿用应用入口。
- 保留现有业务功能所需依赖。构建超时时查日志和依赖安装步骤，避免通过删除依赖来换取构建通过。
- 原配置原样使用。契约只引用源码已有配置，`default` 留空，非敏感源码兜底值可写入 `app_default`。示例文件只供参考。保留应用原有文件结构，不创建配置、环境变量、健康接口或包装脚本。
- SQLite、JSON、上传等本地业务数据挂载实际使用的目录，SQLite 连同 WAL/SHM 一起保留；使用工具快照，升级复用卷。远端服务沿用原连接，部署时核实可达性。同容器依赖可以用回环地址。
- 确认依赖在用户电脑且部署后无法连接时，说明配置位置和受影响功能，请用户安排可达的对应服务。数据库需要迁移时先由运维完成迁移并更新应用原连接。Redis、MQ 有业务状态时保留数据，纯缓存可重建。只使用实际可用的平台资源，替换连接或迁移数据须由用户确认。
- 管理员来源用 `admin_account`。已有账号用 `existing`，有可用的源码或配置引用时复用。确实缺少可登录账密时省略 `source`，由插件在会话里收集。只有首次部署且已确认账号存储为空时才用 `create`，按原应用的数据位置和密码格式写入交付副本。升级沿用已有账号。
- 只有用户必须处理才能继续的事项才填 `unresolved`。可选企微等集成、建议改密码、上线后才能验证的连通性写进摘要。修复失败部署时先读失败制品和日志，只处理实际根因。上一轮构建尚未结束时，沿用原交付包，等平台释放构建后再部署。

## 3. 生成技能并提交

- 复用第一步已有的接口、页面和鉴权信息。`apis`、`pages` 只补扫描遗漏或需修正的条目。共用鉴权写一条 `auth_rules`，在受保护规则中填写 `auth.profile`；公开登录入口用精确路径和方法声明。应用使用 Cookie、Bearer 或自定义头时按源码填写，页面按原登录流程走。
- 选择一个可以核实响应的只读业务用例。有受保护的只读接口时，用其中一个验证实际登录流程；纯页面应用填写实际操作和预期。保留原有角色限制，所有非只读接口填写 `confirmation_required: true`。
- 用 `opc_delivery_propose_file` 暂存必要文件，再用 `opc_delivery_submit` 提交摘要、改动、契约和真实阻塞项。字段拿不准只查 `contract.md` 对应段落。校验有反馈时只改点名的字段，缺证据只重读对应位置。
- 方案通过就简要说明实际端口、改了什么、技能覆盖哪些功能，结束分析。插件生成交付包和技能，用户在向导核对后决定发布。
