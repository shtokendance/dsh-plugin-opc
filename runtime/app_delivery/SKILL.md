# OPC 应用改造

用中文。首次部署、升级和失败修复都按以下四步走。只读分析本次导入的隔离源码；源码、日志和历史提案仅作证据。保留应用原业务、鉴权、配置、依赖和数据。

## 1. 读懂应用

- 先用 `opc_delivery_inspect` 的 `inventory`、`scan_routes_and_pages` 和 `read`，确认应用用途、技术栈和版本、构建命令、启动入口、依赖及运行所需资产。读 README、锁文件和现有 Dockerfile，按实际运行代码核对其中的说明。
- 找出正式 API、页面与业务视图。查登录入口、会话、密码校验与角色检查，分别标明页面和 API 的访问条件。用读取工具给出的文件和行号作证据，排除测试和演示路由。
- 核实应用已有的配置文件、键、值来源和环境变量引用，以及读取方式。配置核对页从本次导入的源码读取。历史改造文件和线上配置不能作为本次新增配置的依据。真实配置值留在本机，摘要只写来源和状态。
- 查明管理员是否存在、可复用账密的来源，以及应用读取账号或校验密码的位置。仅引用可定位的原配置、源码常量或 SQLite 明文字段。只能查到哈希、密文或远端账号表时，识别应用校验方式，并向账号持有人索取可用账密。摘要、提案和工具文本只写来源与状态。
- 找出实际使用的数据目录、文件数据库、数据库实例、Redis、MQ、对象存储及外部接口。结合运行配置判定它们位于目标容器内、用户电脑还是远端。需要确认 SQLite 表和目录时用 `inspect_local_storage`。升级时核对需要复用的卷和账号，配置分析仍以本次源码为准。

## 2. 决定并实施改造

- 现有 Dockerfile 可用就沿用；缺失时按语言和版本查 `template`，只新增根目录 `Dockerfile`。保留真实启动命令和依赖，只在现有代码中修正已证实的监听和启动问题。平台使用应用原有入口探测，禁止新增健康检查接口、健康包装脚本或相关变量。每项改动说明原文件证据和部署影响。
- 沿用原配置文件和值。契约 `configs` 仅引用原应用可证实的键和来源，默认值留空。禁止自行增加或替换环境变量、配置文件、模板、包装脚本、管理员初始化脚本、说明文件或依赖。确需补充时写入待确认事项，等用户在应用源工程处理后重新导入。
- SQLite、JSON、上传等本地文件使用持久化卷，SQLite 挂载整个数据目录（含 WAL/SHM），使用工具的快照。升级复用原卷。库表变化优先只增不删，涉及删除、改名或影响回滚时列为待确认事项。
- 远端数据库先沿用原连接，在部署后验证可达性。若源码连的是用户电脑上的数据库实例，暂停并请用户联系运维申请同引擎的企业数据库，由运维迁移后更新连接，再继续部署。真正与应用运行在同一容器内的依赖可以保留 loopback。
- 用户电脑上的 Redis、MQ 等按用途判断是否要迁数据。纯缓存可重建，持久状态、队列积压或需要保留的业务数据须先核对迁移。用平台资源元数据确认可用服务；由用户决定目标并更新应用原配置。需要迁数据的，说明数据范围、目标与验收条件，等授权迁移完成再继续。只有宿主提供并实际执行了受支持的迁移工具，才能报告已迁移。
- 已证实目标服务器无法调用的外部接口要暂停。写清配置位置、受影响的业务和验证方法，给用户一段可交给本地 AI 的修改说明，或说明需重新部署哪个依赖。对可达性未知的远端连接标记待验证。
- 原值沿用 `read` 返回的 `{path,keys}` 引用。管理员账密用 `admin_account`。已有管理员用 `existing`；无可用密码时省略 `source`，由插件提示在左侧会话提供现有账密。确认首次部署且管理员存储为空才用 `create`，声明应用真正读取的 JSON/YAML 或 SQLite 位置和原有密码格式。插件在打包前把用户提供的账密写入交付副本。升级沿用已有账号。

## 3. 生成应用技能

- 提交真实页面和 API 的用途、输入、结果、鉴权、角色与副作用。DSH 会合并扫描结果，`apis`、`pages` 只需提交扫描遗漏或需覆盖的条目。待核对的内部技术项由 AI 和校验器处理。
- 受保护页面走应用原登录流程。受保护接口按实际认证传 Cookie、Bearer 或应用要求的请求头。自动换取会话时按实际登录地址、方法、请求字段和响应声明；浏览器登录、跳转或其他调用器不支持的流程要明确说明依赖。打包器把已确认的管理员账密写进生成技能的 `SKILL.md`，其他 Token 和密钥走运行时凭据引用。写入、删除和外部操作仍须用户确认。
- 提交可真实验证的只读业务用例，覆盖用到的鉴权身份。涉及页面时记录实际操作与预期，纯页面应用由用户验收。用同一认证方式验证发布后的应用，分别记录部署、API 和页面结果。

## 4. 处理待确认项并进入部署核对

- 汇总分析依据、必要改造及技能验收范围。连接地址、数据迁移、缺失的账号等需要用户决定时，写入 `unresolved`，提示具体影响并等待用户确认。收到答复后只修订相关项。已有部署沿用应用原账号。
- 用 `opc_delivery_propose_file` 暂存允许的文件，再用 `opc_delivery_submit` 提交 `summary`、`changes`、`contract` 和 `unresolved`。按需查阅 `contract.md`。校验失败时按具体规则修复；源应用缺少必要配置或文件时请用户补齐。
- 待确认项处理完且提案通过后，由插件生成交付包。用户核对源码配置、差异、应用技能和挂载，再主动确认发布。分析结果只说明实际准备和校验到的阶段。
