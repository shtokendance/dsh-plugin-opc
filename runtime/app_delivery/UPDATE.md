## 1. 核对新代码与当前线上版本

先读取新版本源码的运行时、配置、端口、路由、鉴权、数据目录和迁移入口。调用 `active_version` 获取当前生效版本的部署清单、有效配置键和挂载，要查上一版具体交付文件时通过 `version_file` 读取。使用成功且当前生效的版本作为基线。更新需要补充新的基础资源时调用 `resources`。

## 2. 只做本次更新需要的改造

- 对照基线检查 Dockerfile、启动与端口，保持兼容的已有配置值、资源、账号、权限和数据卷。新版本确实改变运行要求时，说明来源和影响；在当前部署会话或配置页接收新值，并在第三步供用户核对。
- 对照源码、上一版迁移文件和实际数据结构。专属 PostgreSQL 用 `database_schema` 核对表、列、索引或指定表的行数。应用配置连外部库时按交付格式使用只读连接。
- 明确提交数据计划。只有旧资源和读写格式可兼容且没有独立迁移时，使用 `reuse`。迁移专属 PostgreSQL 时用 `postgres_copy`，选三个互不相同的数据库资源，提交有序 SQL 文件、停写影响、以副本验证的证据和恢复方式。遇到其他无法安全执行的迁移时，把具体缺失能力或外部处理写入 `unresolved`。
- 保留源库和历史写入。演练使用隔离库，正式复制在平台确认旧实例停写后进行。切换失败且已生成迁移回执时，以回执内的目标库作为下一次修复的数据起点。用 `database_schema` 核对目标库，修复版继续沿用它，或从该库向前迁移。
- 只提交本次必要的 Dockerfile、运行配置和迁移文件。旧配置仍有效时沿用，不添加无关工具、变量、健康接口或鉴权。部署失败回到本步，先用 `read_failed` 和日志定位，只修复实际根因。

## 3. 生成新版技能并提交

按 [交付文件格式](references/delivery-files.md) 提交能独立部署的完整契约和新版 SKILL.md。逐项声明必填配置的来源，并对照生效版本说明沿用的数据、权限和密钥。按 [候选版本验收](references/assessment.md) 核对实际运行情况和历史数据。
